Auto Drive 架构深挖候选

当前项目没有 `CONTEXT.md` 或 ADR；以下沿用代码中的 Auto Drive、coordinator、CLI 和 conversation transcript 术语。

1. Auto Drive 生命周期模块

涉及：`code-rs/code-auto-drive-core/src/controller.rs`、`code-rs/tui/src/chatwidget.rs`。

问题：生命周期模块已有 transition 机制，但调用方仍可直接设置运行 phase。controller 和 TUI 中共有 71 处直接 phase 赋值，生产路径也会绕过 transition 校验、review lock 处理和 effect 发送。因此其 interface 偏 shallow：调用方必须同时理解合法的生命周期状态，以及每个状态相应的 UI 和工作流后果。

方案：deepening Auto Drive 生命周期模块，让它独占 phase 变化与其产生的 effects；将原始 phase 修改收回 implementation 内部。

收益：stop、restart、review 和 countdown 行为获得更强的 locality。调用方通过表达意图获得 leverage，而不是编排状态细节。测试可经由该模块的 interface 验证生命周期与 effects，无需构造完整 TUI。

2. Auto Drive coordinator 运行循环模块

涉及：`code-rs/code-auto-drive-core/src/auto_coordinator.rs`。

问题：4,873 行的 coordinator 模块同时处理模型路由、认证、指令发现、prompt 构建、schema 构建、conversation compaction、streaming、retry、acknowledgement 和 event dispatch。理解一次 coordinator turn 必须在同一 implementation 的远距离区域间跳转。

方案：保持 coordinator 现有 external seam，不改变其对外职责；在内部将 turn planning、conversation maintenance 和 decision execution 聚合为职责内聚的 private modules。

收益：prompt/schema、routing 或 acknowledgement ordering 的改变获得 locality，避免影响中央循环。现有 coordinator interface 成为更有用的 test surface，同时以聚焦的内部测试覆盖复杂的 turn preparation 和 recovery。

3. Auto Drive transcript projection 模块

涉及：`code-rs/tui/src/chatwidget.rs`。

问题：`ChatWidget` 将 history cells 转为 coordinator conversation items，解释 diff 和 browser screenshot，处理 compaction overlay，并跟踪 source indices。每增加一种 history cell 都会扩大 TUI 生命周期模块，也使 transcript 正确性难以在不渲染 UI state 的条件下测试。

方案：deepening 一个 transcript projection 模块，负责从可见 Auto Drive history 到 coordinator conversation 的转换以及 compaction 对应关系。

收益：TUI 保留 display concerns；transcript 规则获得 locality。它的 interface 成为 ordering、omission、diff summary、screenshot 与 compaction 的 test surface，无需 terminal harness。

4. 模型路由规范化模块

涉及：`code-rs/core/src/config.rs`、`code-rs/code-auto-drive-core/src/auto_coordinator.rs`、`code-rs/tui/src/chatwidget.rs`。

问题：Auto Drive routing rules 分别在 config loading、TUI 和 coordinator 中独立规范化。规则彼此相关但不共处：修改可接受模型、reasoning levels、defaults 或 authorization eligibility 时，必须追踪多个 modules。

方案：deepening routing-rules 模块，使 validation 和 resolution rules 共处；config persistence、TUI 和 coordinator 在各自的 seams 使用这些规则。

收益：单一改动点改善 locality，并避免 UI/config/runtime divergence。测试一次覆盖 routing behavior；TUI 与 coordinator 的测试只验证各自 adapter 特有的行为。

优先级：生命周期模块最值得先做；它已有 transition interface，却允许绕过该 interface。
