# Plan: 阻止不可重试的 Responses 错误进入无限重连

> **User's request (restated)**: 修复在 `/planning` 使用不支持 `codex-lite` 的
> OpenAI-compatible 上游时，HTTP 400 被显示为流断开并反复重连的问题。
>
> **What this plan answers**: 将明确的上游请求校验失败保留为终态错误，同时维持真实流中断、
> 限流和服务端故障的既有重试行为。
>
> Goal: 用户在首个不可重试的 4xx/协议错误后看到可操作的原始错误信息，且该 turn 不会重发。

## Context

规划模式可切换到独立的 planning model。若该模型启用了 Responses Lite，客户端会在
`include` 中发送 `reasoning.encrypted_content` 与 `codex-lite`。部分兼容端点拒绝后者，返回
`[EnumParam] included[1] invalid value: codex-lite`。当前某条 SSE/stream 错误转换路径将这类
失败构造成 `CodexErr::Stream`；`streaming.rs` 只要尚未产生工具输出便一律重试，因此 UI 持续
显示 Reconnecting。

## Goal

- 400、422 等确定的请求校验错误不会进入流式退避重试。
- UI 保留上游错误正文和 request id（如存在），方便用户修改 provider 或模型配置。
- 网络中断、临时 5xx、可等待的 429 和当前内容过滤处理维持原有策略。
- 为 `codex-lite` 不兼容场景建立稳定回归测试。

## Plan

1. 沿 Responses HTTP 与 SSE/WebSocket 两条接收路径追踪错误：确认哪些事件包含 HTTP status、
   provider error body 与 request id，以及在哪一步被转换为 `CodexErr::Stream`。记录最小的
   可判定错误元数据，避免通过字符串匹配 `codex-lite` 或特定供应商文案。
2. 扩展或复用错误类型，使流内收到的终态上游失败能携带 HTTP status/body/request id；对于
   不能提供 status 的协议，保守地继续沿用现有 Stream 语义，避免把真实网络异常误判为 4xx。
3. 将重试决策集中为“错误类别 + 是否已有工具输出 + 重试次数”的策略。仅允许连接错误、
   显式可重试限流、可恢复的服务端错误及既有 content-filter 分支重试；对请求校验、认证、
   配额和其他明确终态错误直接返回。
4. 更新 TUI 错误呈现，区分“可重试的流错误”和“上游拒绝请求”。后者显示 HTTP 状态、上游
   消息与可用 request id，且不显示 Reconnecting 倒计时。
5. 为配置诊断补充上下文（不记录密钥）：当错误是 `include` 参数不兼容时，提示检查 planning
   model、Responses Lite 与 provider wire API。不要在通用错误处理里硬编码 `codex-lite` 作为
   重试判断条件。
6. 审计 `use_responses_lite` 的启用条件和 planning model 的会话切换。确保非官方 provider
   不会因错误的 provider identity 或 endpoint 分类而继承 OpenAI-only Lite 行为；保留官方
   Responses 端点的 Lite 体验。

## Think — Debug Methodology

- 在 `core/src/client.rs` 的 HTTP/SSE 错误解析与 `core/src/codex/streaming.rs` 的重试决策边界
  添加短期或现有结构化日志，记录状态码、错误分类、request id、是否有工具输出及重试决定；
  不记录 Authorization、请求正文或 API key。
- 先用本地 mock Responses 服务返回一条与截图等价的流内/HTTP 400，再确认客户端错误类型，最后
  才修改分类逻辑。不能先从 UI 文案推断底层错误。
- 搜索所有 `CodexErr::Stream` 构造点、`UnexpectedStatus` 返回点和
  `should_retry_stream_after_error` 调用者，避免仅修复 SSE 而遗漏 WebSocket 或 follow-up turn。
- 用 provider identity、endpoint 分类、model family 与 `use_responses_lite` 的实际值定位为什么
  当前 planning model 带上 `include[1]`，而非假设所有第三方源均相同。

## Do — Verification Strategy

- **Build**: 从仓库根目录运行 `./build-fast.sh`，必须零错误、零警告通过；不运行 rustfmt。
- **回归测试**: 在 `code-rs` 增加本地 mock-server 测试，返回
  `400` 与 `included[1] invalid value: codex-lite`，断言只收到一次请求、结果为终态错误且正文可见。
- **重试边界**: 覆盖无工具输出的网络断开/可重试 429 或 5xx 仍重试，以及已有工具输出时仍不重试。
- **模式覆盖**: 覆盖普通聊天与 planning model 会话切换；验证不兼容 provider 不会错误开启
  Responses Lite，官方 Lite 路径仍会发送所需参数。
- **手工验证**: 在 TUI 使用该 mock provider 执行 `/planning painpoints/pp12.md`，确认不出现
  Reconnecting，错误指出上游不支持的参数；改用兼容模型或 Follow Chat Model 后可继续提交。

## Adjust — Rollback and Global Scan

- **Rollback plan**: 将新分类限制在 provider 已提供明确 HTTP 4xx 的流错误转换处；若出现协议
  兼容问题，可回退该映射而不改变网络中断和限流的原有重试策略。
- **Global scan**: 检查 Responses HTTP、SSE、WebSocket、Chat Completions 适配器、Auto Drive、
  子 agent 与 tool-result follow-up 是否共享同一终态错误和重试判定。
- **Backwards compatibility**: 不改变官方 Responses Lite 请求格式，也不改变用户设置的重试次数；
  仅阻止先前被误标为 `Stream` 的明确不可重试错误再次发送。

## Open Questions

- 当前的 400 是初始 HTTP 响应还是 SSE/WebSocket 已建立后送达的 error event？实现应由复现结果
  决定最小改动位置。
- 对于没有 HTTP status 的兼容端点 error event，是否能从标准错误结构可靠标识为参数校验失败，
  还是应一律保守重试？
- provider profile resolver 是否存在把自定义端点标记为官方 `openai` 的路径，从而错误开启
  `use_responses_lite`？

## Out of Scope

- 为不支持 Responses Lite 的第三方网关实现协议转换或自动降级请求。
- 修改第三方 provider 的服务端实现或其模型能力声明。
- 改变 planning skill 的计划生成内容、文件路径或权限语义。

### [Risk] 过宽的终态分类吞掉了本应重试的短暂故障

**Severity**: 5 | **Likelihood**: 3 | **Detectability**: 0.10
**Risk Score**: 13.5 — HIGH

**Failure Scenario**: 实现将所有带错误正文的流失败都视为不可重试，某些网关在连接抖动、
过载或临时认证刷新期间返回非标准 4xx/错误 event；用户因此失去原本能成功的自动恢复，
表面上“修复无限重连”却显著降低成功率。

**Mitigation**:

- 以显式 HTTP status 和结构化的 provider 错误分类作为终态依据；未知、缺少 status 的 stream
  error 保持现有保守重试语义。
- 将重试策略写成表驱动或穷尽 match，并为 400/401/403/422、429、5xx、连接超时和未知 stream
  error 分别添加测试。
- 在结构化日志中记录最终分类和“不重试”的原因，先通过测试与开发日志审查再扩大覆盖范围。

## Post-Mortem

**Date**: 2026-11-04

### Issues Fixed

| # | Severity | Type | Location |
|---|---|---|---|
| 1 | High | Error-classification loss | `core/src/client.rs` WebSocket-to-SSE bridge |
| 2 | Medium | Missing diagnostic context | `core/src/client.rs` SSE transport handling |
| 3 | Medium | Unbounded error output | `core/src/client.rs` structured provider error body |

1. The WebSocket adapter correctly decoded a 400 as `UnexpectedStatus`, but `process_sse` rewrapped
   it as `Stream`; the retry loop then resent an invalid request. Terminal transport errors now retain
   their type and therefore bypass retry.
2. WebSocket errors do not always include a request id. The bridge now attaches the active SSE request
   id when absent, preserving actionable diagnostics.
3. Structured provider error messages now retain only the documented fields and cap `message` at
   600 Unicode scalar values. This avoids placing arbitrarily large upstream text in terminal history
   or session logs.

### High-Risk Closure

| Pre-mortem risk | Closure evidence | Status |
|---|---|---|
| Over-broad terminal classification | Only explicit standard terminal error types map to `UnexpectedStatus`; unknown stream errors remain retryable and are covered by unit tests. | Closed |
| SSE/WebSocket path divergence | `response.failed` mapping plus a WebSocket-to-SSE transport-error regression test cover both error entry paths. | Closed |
| Incorrect Responses Lite activation | Existing configuration coverage proves custom and proxied endpoints disable Lite while the official endpoint retains it. | Closed |
| Sensitive or oversized provider error body | The bridge emits only structured error fields and the message is bounded; regression coverage verifies truncation. | Closed |

**High risks remaining: 0.**
